## 2. Current lifecycle map

The current path is:

1. `Blockchain.cast_submission_vote()` (`blockchain.py:1851`) delegates to
   `SubmissionOriginalityService.cast_submission_vote()`; it reads submission
   and vote lists, rejects duplicate voter/submission pairs, appends a vote,
   and the operation wrapper saves the whole state. Vote insertion order and
   `time.time()` are current inputs unless the caller supplies `created_at`.
2. `Blockchain.evaluate_submission()` (`blockchain.py:2117`) reads votes,
   submission status, active-user activity, and wall-clock time. On approval it
   calls `create_originality_certificate()`.
3. `SubmissionOriginalityService.create_certificate()`
   (`services/submission_originality_service.py:100`) checks for an existing
   certificate, promotes content, creates an
   `OriginalityCertificate.from_approved_submission()` record, validates it,
   appends it, and links `submission.certificate_id`. The approval path saves
   once after certificate creation, then changes submission status to
   `APPROVED`, validates again, and saves again (`blockchain.py:2168-2184`).
4. `Blockchain.add_to_mint_queue()` (`blockchain.py:2223`) calls
   `MintQueueService.add()` (`services/mint_queue_service.py:42`), which checks
   the certificate/content eligibility, appends the submission ID to the
   in-memory authoritative queue, and changes status to `QUEUED`. The caller
   controls when `save_blockchain()` runs.
5. `mint_next_queued_submission()` (`blockchain.py:2256`) scans
   `self.mint_queue` from left to right, evaluates each item, and selects the
   first currently mintable record. It then resolves the certificate and calls
   `_mint_submission_record()`.
6. `_mint_submission_record()` (`blockchain.py:2231`) calls `add_block()` with
   the submission media/certificate. `BlockProductionService.build_candidate()`
   (`services/block_production_service.py:46`) embeds the full Model A media,
   selects native transactions, validates legacy transactions concurrently,
   creates reward transactions/metadata, derives `index = latest.index + 1`
   and `previous_hash = latest.hash`, and uses `time.time()` for block and
   mint timestamps.
7. `add_block()` calls `accept_block_candidate()`
   (`blockchain.py:2529` and `2474`). Candidate validation is delegated to
   `BlockValidationService.validate_candidate()`; then acceptance mutates the
   wallet/reward balance, appends the block, settles native transactions,
   removes selected legacy pending transactions, rejects skipped native
   records, updates duplicate-detection caches, recomputes the reward pool,
   and saves.
8. `NativeLedgerService.settle_block_native_transactions()`
   (`services/native_ledger_service.py:415`) records each block-native
   transaction if absent, then marks it `settled` with block hash/height and
   settlement time. Native balances and nonces are derived from canonical block
   transactions by `calculate_balances_from_chain()` rather than stored as
   independent canonical account state.
9. `_mint_submission_record()` calls
   `reconcile_submission_canonical_state()` and removes the queue entry/statuses
   are set to `MINTED` when the block reference is observed, then saves again.
   Voter reward records are represented in block metadata/transactions and
   considered settled by deterministic reward IDs; creator reward metadata is
   generated by `RewardService`.
10. `FinalityService.block_chain_state()` (`services/finality_service.py:51`)
    derives canonical confirmations from tip height minus target block height.
    Public lifecycle serializers expose `confirmations`, `confirmed`,
    `finalized`, depths, model, and scope through the submission/block APIs.

## 3. Ownership boundaries and durable state

- `Blockchain` (`blockchain.py`) owns authoritative collections, facade
  assembly, load/save, candidate acceptance, chain replacement, canonical
  reconciliation, wallet bookkeeping, and orchestration.
- `MintQueueService` owns queue admission/evaluation/blocking/removal rules,
  not candidate construction or persistence.
- `SubmissionOriginalityService`, `submission.py`,
  `originality_certificate.py`, and `protocol_v1_originality.py` own vote,
  threshold, certificate, and status rules.
- `BlockProductionService` owns candidate assembly and native/reward selection
  metadata. `BlockValidationService` owns validation only.
- `NativeMempoolService` owns deterministic mempool sorting, admission,
  revalidation, and block candidate selection. `NativeLedgerService` owns
  signed transaction identity, nonce/balance calculations, settlement, and
  reconciliation.
- `RewardService` owns deterministic creator/voter reward planning and reward
  IDs. Rewards are materialized as block transactions/metadata; no separate
  atomic reward ledger exists.
- `ForkChoiceService` owns score/height/tip-hash comparison. `FinalityService`
  owns derived depth views.
- `storage.py` owns JSON and SQLite adapters. `api_routers/`, `api_runtime.py`,
  and `peer_sync.py` are adapters/facades; peer acceptance ultimately calls
  `Blockchain` validation/replacement paths.

## 4. Mint ordering

Certified ready submissions are ordered by the list order of
`Blockchain.mint_queue`. `MintQueueService.add()` appends IDs, and
`mint_next_queued_submission()` scans that list without sorting. Therefore the
current policy is insertion/FIFO order, but it is not a protocol-level
deterministic ordering: concurrent admissions can race on append/save order,
and a queue reconstructed from external or legacy state inherits that order.

There is no timestamp or score tie-breaker for mint candidates. Within a block,
native transactions are sorted by `(from_address, nonce, tx_id)`; mempool
listing is sorted by `(admitted_at or updated_at or created_at, from_address,
nonce, tx_id)`. Voter rewards are sorted by finalized time/submission ID/wallet
for due records, with the prioritized current submission handled first. These
are transaction/reward ordering rules, not ready-submission mint ordering.

## 5. Height and head mutation

`BlockProductionService.build_candidate()` reads `state.chain[-1]` and captures
the next height and previous hash at lines 182-192. Candidate validation then
checks against the chain passed by the facade, but `accept_block_candidate()`
does not re-read or compare the live head immediately before `self.chain.append()`.
There is no compare-and-swap, per-chain lock, unique height constraint, or
storage-level expected-head update. Two concurrent builders can therefore both
construct the same height/previous hash; both can validate against a stale
head, and both can append in one process. Interleaved persistence can also lose
one update. The current protection is ordinary Python list/process behavior and
validation at the time of each call, not serialized canonical commitment.

## 6. Persistence atomicity and crash windows

`Blockchain.save_blockchain()` serializes the complete facade state and calls
`StorageBackend.save_blockchain_state()` (`blockchain.py:356-359`). JSON uses a
temporary file, fsync, atomic replace, and a `.bak`; SQLite rewrites all
sections inside one SQLite transaction (`storage.py:940-988`). That makes an
individual whole-state save recoverable, but it does not make the in-memory
mutation sequence and save one transaction, nor does it coordinate multiple
processes reading stale snapshots.

One content block currently requires durable mutation of: chain; canonical
position implicitly represented by chain order; legacy pending transactions;
native transaction records and transfer-intent statuses; wallet miner credit;
reward-pool-derived state; submission status/queue; certificate linkage; reward
metadata/settlement represented in the block; duplicate caches; and content
objects if content promotion occurred earlier. These are not all committed by
one domain transaction. The main crash windows are:

- after certificate append or the first approval save but before the status
  transition/second save;
- after block append but before native settlement, pending removal, cache and
  final save;
- after native settlement but before the enclosing block save;
- after block save but before submission reconciliation/final queue save;
- during separate queue/certificate/submission API operations;
- concurrent whole-document JSON saves (last writer wins), and concurrent
  SQLite saves that serialize individual save calls but can still persist a
  stale caller snapshot after the prior writer commits.

The JSON atomic replace protects file replacement and backup recovery, and the
SQLite `_save_sections()` transaction protects its own section rewrite. Neither
provides a block-commit transaction with an expected canonical head.

## 7. Idempotency and replay protection

Existing protections are mixed:

| Item | Current protection | Assessment |
|---|---|---|
| Submission minting | status checks; protocol block lookup by submission/certificate; canonical reconciliation | Application-level only; race remains between checks and append. |
| Certificate consumption | one certificate lookup per submission; deterministic certificate ID/linkage; block validation linkage | No atomic consume/reserve operation; concurrent creation is only locally checked. |
| Block insertion | hash/block validation and chain validation; no height/head uniqueness constraint | No atomic insertion/idempotency key. |
| Block height | derived from current last list item | No persistence constraint or compare-and-swap. |
| Native transaction settlement | tx IDs and duplicate checks in validation; settlement updates by tx ID | Good replay checks after state is canonical, but settlement plus block append is not atomic. |
| Sender nonce advancement | nonce validation against chain and reserved statuses; chain replay checks | Application-level; concurrent reservations can both observe the same next nonce. |
| Creator rewards | duplicate meme reward detection by submission ID during balance reconstruction | No separate reward settlement record/unique constraint; block race remains. |
| Voter rewards | deterministic reward IDs and settled-ID checks in reward planning/validation | No atomic claim; concurrent candidates can select the same pending reward. |

`record_native_transaction()` returns an existing tx by `tx_id`, and restore
logic removes duplicate IDs/conflicting unavailable nonces. These are useful
database-independent checks, not database constraints: the JSON backend has no
entity tables/unique indexes, and SQLite stores JSON sections rather than
normalized block/tx/reward rows.

## 8. Finality

Current finality is confirmation-depth based. `FinalityPolicy` defaults to
`confirmation_depth=2`, `finality_depth=6`, `finality_model="operational_depth"`,
and `finality_scope="policy_not_bft"` (`services/finality_service.py:7-13`,
configured through Protocol v1 constants). Confirmations are
`canonical_tip_height - block_height`; `confirmed` and `finalized` are derived
from the two thresholds. States exposed include none, canonical, confirmed,
and finalized, plus accepted/block-created/block-accepted flags.

This is reorg-sensitive because the view is recalculated from whichever chain
is currently canonical. `Blockchain.replace_chain()` compares chains using the
fork-choice service, replaces the chain, recomputes the reward pool, reconciles
submissions and native transactions, but does not provide irreversible finality
evidence. No validator quorum, validator signatures, attestations, or finality
certificate were found. Public submission/block lifecycle and chain responses
expose the depth fields and the explicit non-BFT model/scope.

## 9. Fork choice

`ForkChoiceService.compare()` first requires matching genesis and a valid
candidate chain, then ranks cumulative originality score, chain height, and
lower latest block hash (`services/fork_choice_service.py:66-97`). If two valid
blocks exist at the same height, the chain with higher cumulative originality
wins; if tied, the lower tip hash wins. Equal tip hashes are equivalent.

`Blockchain.replace_chain()` performs the actual replacement and canonical
reconciliation. This remains relevant for peer synchronization and reorg
handling. It does not serialize local block creation and should not be treated
as protection against two local commits at one height; Milestone 3 can retain
the ranking rule while making local canonical commitment single-writer.

## 10. Concurrency and crash hazards

The acceptance criterion of 100 simultaneous approvals producing exactly 100
sequential blocks is not currently guaranteed. Concrete hazards are:

- concurrent vote/certification operations can observe the same pre-transition
  submission state or queue and perform separate whole-state saves;
- queue order is append/interleaving order, not a canonical ready-set order;
- candidate construction captures a stale head and stale reward/native state;
- no final head recheck prevents duplicate heights/stale previous hashes;
- duplicate submission/certificate checks are outside the append/save boundary;
- native nonce reservation is list-based and non-atomic;
- native transaction selection and legacy transaction validation observe a
  moving in-memory state; the legacy validation uses a thread pool, while
  result consumption follows submission-map order and reward-pool arithmetic
  depends on mutable candidate state;
- the same voter reward can be selected by concurrent candidates before either
  block is canonical;
- `accept_block_candidate()` mutates many collections before save, so an
  exception or process crash can leave memory partially applied and a prior
  durable snapshot on disk;
- JSON last-writer-wins saves can lose blocks/queue/status changes; SQLite
  serializes save transactions but callers still load and merge stale complete
  documents, and its default connection has no application-level busy/retry
  policy;
- peer chain replacement can rebase canonical-derived statuses while a local
  mint is being accepted.

Parallel preparation is currently plausible, but canonical commit must be
serialized and must revalidate head, candidate uniqueness, native settlement,
rewards, and submission consumption in one later task.

## 14. Remaining uncertainties and risks

- The branch name indicates Milestone 3 intent, but its ref is currently equal
  to `origin/main`; no remote branch-specific ancestry marker exists in the
  local repository.
- The facade still contains some compatibility/legacy paths alongside
  Protocol v1 paths; future tests must clearly select the certified Model A

  consensus entities, so a safe atomic commit design must define snapshot,
  expected-head, backup, and recovery semantics explicitly.

  any future quorum work must not silently reinterpret existing fields.

  3.1; production code, APIs, fork choice, ordering, idempotency, and finality
  behavior were not changed.
